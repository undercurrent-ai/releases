BreachRadar

Breach monitoring and an outreach queue, on your own machine

Watches SEC EDGAR 8-K Item 1.05 filings and six incident-press feeds, and puts every new disclosure in front of you as a triage queue rather than a dashboard you have to remember to open.

Eight columns from Inbox to Call booked. The day counter on each card is computed as it renders, so a target sitting in Hold turns colour by itself on the morning it enters the window you care about. Nothing is auto-filed into an outbound column — extracting an organisation from a headline is a heuristic and it is wrong often enough to matter.

No daemon, no API keys, no telemetry and no server. It polls when you open it, or once a day at most. Your board, notes and settings stay in a folder in your home directory and an update never touches them.

Breach Radar 0.3.1

Reserving a workspace speaks the outreach v2 contract (undercurrent-ai/site → docs/OUTREACH_ACQUISITION_API.md).

  • One claim code per contact. When a card has contacts, a new checkbox on

the Workspace tab gives each of them their own code, with a role suggested from their title (CISO, Deputy CISO, Head of IR, IT Director → admin; others → member). The codes are shown once, with copy buttons, and are not stored on this Mac — Helm → Acquisition reveals them again when needed.

  • The server picks the subdomain. Leave the field blank and the name is

reduced to a short, distinctive slug ("Sutter Health Vallejo" → sutter-vallejo); type one to override it.

  • Never a second workspace for the same company. Reserving a company that

already has a workspace — the same card again, or the same company from a different feed — adds codes for new people only.

  • Provenance travels with it. Name, industry, ICP score, incident kind,

filing date and board column go up as workspace metadata, so "why does this company have one" is answerable from the console.

Unchanged: with the checkbox off, the workspace carries the single org-level code the third-touch template reads, exactly as in 0.3.0. A v1 server still accepts everything this version sends.

The store moved

Breach Radar is on the house app-data standard now. Your board lives at ~/.undercurrent/db/breachradar/ and the app no longer contains any database code — it shells to cli/breachradar, which owns the store.

Nothing to do, and nothing to lose: the first launch imports your existing board, and the old ~/.undercurrent/breachradar/breachradar.sqlite3 is left exactly where it is and never written to again.

What you get for it: every launch, release and install is recorded, so ucdb ls can tell you which build you are running and since when; every write carries an audit entry; and a Claude session can now read and repair exactly the board you are looking at, with the same code the app uses, instead of a second reader that has to be kept in step.

One safety change worth knowing about. The page hands the whole board to the store on every change, which means a caller holding a short board is implicitly asking for everything missing from it to be deleted. The store now refuses a save that would remove more than about a third of the board, and says so. It caught a real bug during this migration — a load that ran a fraction of a second too early returned an empty board, and the next save asked to remove 84 cards. Deletions are tombstones regardless, so nothing was actually lost.

First launch. These builds are ad-hoc signed, so macOS asks once. The one-time steps are here — later updates are installed by the app itself and never hit that prompt.
